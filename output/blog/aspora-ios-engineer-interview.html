02 Most Asked Questions

Most Asked Questions

Based on the nature of the product and what iOS candidates commonly report at fintech companies, expect questions across these themes:

  1. How have you implemented secure local storage for sensitive user data (tokens, account numbers) in an iOS app?
  2. Walk me through how you would architect an offline-first feature in a payments or remittance app.
  3. How do you handle network failures and retries gracefully without frustrating the user?
  4. Explain your experience with Swift Concurrency (async/await, actors). How would you use it for parallel API calls?
  5. How have you implemented biometric authentication (Face ID or Touch ID) and what security considerations did you keep in mind?
  6. Describe how you have handled multi-currency display and locale-specific number formatting in an iOS app.

  8. Walk me through a performance problem you debugged using Instruments. What was the root cause and how did you fix it?
  9. How would you design the push notification system for real-time transaction alerts, including deep linking from the notification?
  10. Tell me about a time a product decision conflicted with your technical recommendation. How did you handle it?
  11. How do you manage Apple OS release cycles: testing betas, handling deprecation warnings, and updating the app before a major release?
  12. Describe your approach to code review. What do you look for and how do you give feedback to a junior teammate?

03 Sample Answers (STAR Format)

Sample Answers (STAR Format)

Q: How have you implemented biometric authentication in a production app?

*Situation:* At my previous company, we had a mobile banking app where users had to type their PIN every time they opened the app. Drop-off at the login screen was a reported concern in user feedback.

*Task:* I was asked to add Face ID and Touch ID support while keeping the authentication flow secure and not breaking the existing session logic.

*Action:* I used the LocalAuthentication framework with LAContext to evaluate the biometry policy. I stored the session token in the Keychain with the 'whenPasscodeSetThisDeviceOnly' accessibility flag and tied it to biometric access using the biometryAny access control option. I also added a fallback to PIN entry, and wrote UI tests covering the 'biometry not available' and 'biometry locked out' states.

*Result:* The feature shipped without any security incidents. Internally, the team noted that login-related support tickets dropped noticeably after the rollout.

---

Q: Tell me about a performance problem you found and fixed.

*Situation:* In a transaction history screen, the list would stutter when the user scrolled quickly through hundreds of entries, each displaying a formatted currency amount and a small icon.

*Task:* I needed to find the root cause without guessing and fix it in a way that held up under regression testing.

*Action:* I profiled with Instruments using the Time Profiler and Core Animation instruments. I found two issues: currency formatting was happening on the main thread inside cellForRowAt, and images were being decoded synchronously. I moved the NumberFormatter creation outside the cell (it is expensive to initialise repeatedly) and used a background queue with prefetching to decode images before they appeared on screen.

*Result:* Scroll performance became smooth and consistent. The fix also reduced CPU spikes during fast scrolling, which teammates confirmed in testing on older devices.

---

Q: Describe a time a product decision conflicted with your technical recommendation.

*Situation:* The product team wanted to ship a feature that cached sensitive transaction data in UserDefaults for speed, which I felt was a security risk for a financial app.

*Task:* I needed to push back constructively without blocking the release timeline.

*Action:* I wrote a short internal document comparing UserDefaults (unencrypted) vs Keychain vs an encrypted local store, with a rough implementation cost for each option. I proposed using the Keychain for small token-sized data and flagged the specific risk: on a jailbroken device, UserDefaults can be read without special permissions.

*Result:* The product manager agreed to the Keychain approach for the first release. We deferred the encrypted store to the next sprint. The feature shipped on schedule with the safer implementation.

04 Answer Frameworks

Answer Frameworks

STAR for behavioural questions: Lead with the Situation and Task in one or two sentences, spend most of your time on the Action (what you specifically did, not 'we'), and close with a concrete Result. If you do not have a number, describe an observable outcome: 'users stopped filing that complaint' or 'the team adopted it as the standard pattern.'

For system design questions: Open by clarifying scope. Ask whether this is for thousands of users or millions, and whether it needs offline support. Then sketch the architecture top-down: screen flow, data layer, networking layer, and local persistence. For a fintech product like aspora's, always call out your approach to security (Keychain, certificate pinning, encrypted storage) explicitly. Interviewers in this space want to see that security is not an afterthought.

For debugging or technical deep-dives: Use a diagnose-first structure. Name the symptom, name the tool you used to investigate (Instruments, Xcode Memory Graph, OSLog), name what you found, and then describe the fix. Avoid jumping to 'I just rewrote it' without showing you understood the root cause.

For code review or architecture questions: Show that you balance pragmatism with quality. It is fine to say 'we shipped it with a known limitation and documented the tech debt,' as long as you explain the trade-off you made consciously.

05 What Interviewers Want

What Interviewers Want

Fintech iOS roles like this one typically require a candidate who treats security as a first-class concern, not something to add at the end. Expect interviewers to probe whether you know the difference between what is convenient (UserDefaults, plain HTTP caching) and what is appropriate for financial data (Keychain, certificate pinning, encrypted stores).

Ownership over execution. aspora is reportedly a growth-stage company, which means interviewers often prefer candidates who have driven features end-to-end: from clarifying requirements to shipping and monitoring, not just implementing a ticket.

Swift fluency, especially modern concurrency. Candidates who describe every async task purely in terms of DispatchQueue and completion handlers without mentioning async/await may appear behind the curve. Know both, and know when to reach for each.

Cross-border product empathy. Given aspora's focus on diaspora users sending money across borders, an interviewer may probe whether you have thought about locale handling, currency formatting, and making an app work well on slower networks. This is central to the product, not a bonus.

Communication. In a remote or hybrid team, written communication about technical decisions (pull request descriptions, design documents) matters as much as coding ability. Some interviewers will ask how you document your decisions.

06 Preparation Plan

Preparation Plan

Week 1: Swift and iOS fundamentals review
Revise Swift Concurrency (async/await, actors, task groups). Practise writing clean MVVM code with Combine or async streams. Revisit memory management: strong, weak, and unowned references, and where each belongs. Review the Keychain API and LocalAuthentication framework in detail.

Week 2: System design and security
Practise designing features like 'transaction history with offline support' or 'real-time notification for an international transfer.' For each design, explicitly call out how you handle sensitive data at rest and in transit. Review certificate pinning and URLSession configuration for secure networking.

Week 3: Behavioural prep and company research
Write out 6-8 STAR stories covering: a security trade-off you navigated, a performance win, a conflict with a product or design decision, and a time you reviewed or mentored someone else. Read aspora's app reviews on the App Store and any publicly available product announcements to understand the user experience you would be building.

Week 4: Mock interviews and refinement
Do at least two timed mock coding sessions in Swift. Practise explaining your thought process out loud. Prepare 3-5 questions to ask the interviewers about the engineering team, the release cadence, and how they handle Apple OS upgrades.

07 Common Mistakes

Common Mistakes

Treating security as optional. In fintech interviews, saying 'I would store it in UserDefaults for now and make it secure later' is a strong negative signal. Always lead with the secure approach and explain the trade-off explicitly if you choose a simpler one.

Vague STAR answers. Saying 'we improved performance' without describing what you personally did or what the outcome looked like is forgettable. Be specific: name the tool, name the root cause, describe the result in observable terms.

Ignoring locale and internationalisation. For a product serving diaspora users across multiple countries, treating currency formatting or right-to-left layout as an afterthought suggests you have not thought about the actual users.

Over-engineering in system design. Adding a message queue or microservice backend to a design that a simpler approach would handle is a common trap. Always explain why your choice matches the stated scale and requirements.

Not asking questions. Candidates who ask zero questions at the end of a round often appear uninterested. Prepare at least two specific questions about the team, the product challenges, or the technical decisions they are actively working through.

Skipping test coverage. If the interviewer asks you to write a function, add at least one test case or describe how you would test it. Fintech companies typically care deeply about reliability.
