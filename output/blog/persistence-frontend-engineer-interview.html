02 Most Asked Questions

Most Asked Questions

Candidates report that Persistence frontend interviews focus on JavaScript core concepts, React depth, and practical problem-solving for enterprise-grade products. These are the questions that come up most often:

  1. Explain the difference between == and === in JavaScript. When would you actually use ==?
  2. How does React's virtual DOM work, and why does it make updates faster than directly touching the real DOM?
  3. What is event bubbling and event capturing? Walk me through a real scenario where the difference matters in a UI.
  4. How would you diagnose and fix a React app that is re-rendering too often and feels slow to the user?
  5. What is the difference between useEffect and useLayoutEffect? Give a concrete example of when you would reach for useLayoutEffect.
  6. How do you implement code splitting and lazy loading in a large React application?
  7. You are building a dashboard that calls five different APIs. How do you handle loading states, errors, and race conditions cleanly?
  8. Compare Redux, React Context, and lighter libraries like Zustand for managing global state. How do you decide which to use?
  9. What is CORS, and if your frontend is throwing a CORS error, what are your steps to diagnose and resolve it?
  10. How have you improved the accessibility of a web application? Which guidelines do you follow and how do you verify compliance?
  11. How do you approach writing unit and integration tests for a React component that fetches data from an external API?
  12. Persistence builds enterprise data products. Describe a project where you integrated a complex REST or GraphQL API and how you handled authentication and error responses end to end.

03 Sample Answers (STAR Format)

Sample Answers (STAR Format)

Q: How would you diagnose and fix a React app that is re-rendering too often?

*Situation:* At my previous company, we had a client-facing analytics dashboard built in React. After a major feature release, users started complaining that the page felt sluggish whenever they changed filter values.

*Task:* I was asked to investigate the performance issue and reduce the interaction lag to a point where the UI felt responsive again.

*Action:* I opened the React DevTools Profiler, recorded a filter interaction, and found that a large data table component was re-rendering on every keystroke even though its own props had not changed. I traced the cause to a parent component creating a new callback function on every render. I wrapped that callback in useCallback, moved a derived data calculation into useMemo, and wrapped the table component itself in React.memo. I also added a short debounce on the filter input to batch rapid keystrokes before they triggered state updates.

*Result:* The unnecessary re-renders were eliminated for that interaction. The filter response felt immediate to users, and the team adopted these patterns as a standard checklist item for future component reviews.

---

Q: Tell me about a time you handled a complex API integration on the frontend.

*Situation:* I was building an internal operations portal where the frontend needed to pull data from three separate microservices, each owned by a different backend team with its own release cadence.

*Task:* I had to display a unified view combining user profile data, transaction history, and live inventory status on a single page load, without one service failure blocking the others.

*Action:* I used Promise.allSettled so that a failure in one service would not prevent the other two from rendering. I built a small status layer in the component state to show partial data with a clear message like 'Could not load this section' where a fetch failed, rather than leaving the user on a blank screen. I also worked with the backend teams to agree on a consistent error response shape so the frontend could handle failures uniformly across all three services.

*Result:* The page handled partial failures gracefully, which significantly reduced user-reported blank screen complaints. The same pattern was reused across three other portal pages later in the project.

---

Q: How have you improved accessibility in a web application?

*Situation:* During an internal audit at my previous company, our customer-facing portal failed several WCAG 2.1 AA checks. The issues included missing alt text on icon buttons, broken keyboard navigation in modal dialogs, and low color contrast on primary action buttons.

*Task:* I was assigned to fix the highest-priority accessibility issues before a client review that was four weeks away.

*Action:* I went through the audit report, prioritized findings by severity, and worked through them one by one. I added descriptive aria-label attributes to all icon-only buttons, implemented focus trapping inside modal dialogs using a focus management utility, and worked with the design team to update the color tokens for action buttons after verifying contrast ratios. I used the axe browser extension to verify each fix before marking it resolved.

*Result:* We cleared all critical and high-severity findings before the client review. The client specifically called out accessibility as a strong point in their post-review feedback.

04 Answer Frameworks

Answer Frameworks

For JavaScript or React concept questions, use a three-part structure: define the concept plainly, explain why it exists or what problem it solves, then give a short code example or real-world analogy. This shows you understand the 'why', not just the syntax.

For debugging or optimization questions, walk through your diagnostic process step by step. Name the tools you reach for first (React DevTools Profiler, browser Network tab, Lighthouse), then explain how you narrow down the root cause before touching any code. Interviewers want to see a methodical thinker, not someone who jumps to solutions.

For architecture or design questions (state management, API integration, code splitting), use a trade-off format: 'Option A works well for X but adds Y overhead. Option B handles Y better but introduces Z complexity. For this scenario I would choose A because of the team size and data flow patterns.' Showing that you can weigh options signals senior-level thinking.

For behavioral questions, use STAR: Situation (one to two sentences of context), Task (your specific responsibility), Action (what you did, in detail), Result (the measurable or observable outcome). Keep Situation and Task brief so you have time to go deep on the Action, which is what the interviewer actually wants to hear.

For enterprise or product context questions, which are common at Persistence given their data-product focus, tie your answer back to business impact: faster page loads for end users, fewer production incidents, improved developer velocity for the team. Enterprise clients care about reliability and maintainability, so show that you think beyond 'it works on my machine'.

05 What Interviewers Want

What Interviewers Want

Persistence hires frontend engineers who can contribute to long-running enterprise projects, not just short product sprints. Based on what candidates report, here is what interviewers look for:

Solid JavaScript fundamentals. Not just React knowledge. Interviewers probe closures, the event loop, prototypal inheritance, and async patterns. If you can only describe React hooks without understanding what is happening underneath, that is a gap they will notice quickly.

Component design for scale. Can you design a reusable component or shared UI module that other teams can consume without breaking their own code? Clear prop APIs and separation of concerns matter in a company building enterprise products across multiple teams.

API integration experience. Persistence products connect to complex backend systems. They want engineers who have hands-on experience handling authentication flows, error states, retry logic, and data transformation on the frontend side.

A testing mindset. Candidates report being asked specifically about testing strategies. Know the difference between unit, integration, and end-to-end tests, and have a clear opinion on when each type is worth the effort in a production codebase.

Clear technical communication. Enterprise client work involves collaborating across teams and sometimes explaining decisions to non-frontend colleagues. Interviewers notice whether you think out loud clearly during technical rounds.

Ownership and follow-through. Behavioral questions at Persistence tend to probe whether you took a problem all the way to resolution or handed it off early. Have stories ready where you drove something from first diagnosis to production fix.

06 Preparation Plan

Preparation Plan

Week 1: Strengthen the fundamentals

Revise core JavaScript topics: closures, the event loop, promises and async/await, prototypal inheritance, and how this binding works. These come up in almost every Persistence frontend interview, candidates report. Solve five to eight JavaScript-focused problems on a coding platform to build confidence before moving to React-specific topics.

Week 2: Go deep on React

Revisit the React hooks lifecycle (especially useEffect dependency arrays), the reconciliation algorithm, and performance optimization tools (React.memo, useMemo, useCallback). Build or rebuild a small project that implements lazy loading and talks to a live API. Hands-on practice surfaces gaps that reading documentation alone will not reveal.

Week 3: System design and API integration practice

Practice designing a frontend for a data dashboard or admin portal out loud, as if explaining to a panel. Cover component hierarchy, state management choice, API error handling strategy, and loading states. Also review CORS, authentication headers (JWT, OAuth flows), and how you would handle token refresh transparently on the frontend.

Week 4: Testing and behavioral prep

Write meaningful tests for the project you built in Week 2 using React Testing Library or Jest. Prepare three to five STAR stories covering debugging, API integration, performance improvement, and cross-team collaboration. Practice saying them out loud, not just thinking through them in your head.

On the day

Think out loud during every round. Candidates report that Persistence interviewers value your reasoning process as much as the final answer. If you are uncertain about something, say so and reason through it rather than going silent.

07 Common Mistakes

Common Mistakes

Knowing React but not JavaScript. Candidates who cannot explain what is happening under the hood in a useEffect or why a closure causes a stale state bug tend to struggle at Persistence. Do not skip fundamentals in favour of framework-only prep.

Vague optimization answers. Saying 'I would use React.memo' without explaining the symptom you diagnosed first signals shallow knowledge. Always connect your solution to a specific problem you identified through profiling or observation, not guesswork.

Only thinking about the happy path. When asked to design a data-fetching component, many candidates describe only the successful case. Persistence builds products where partial failures happen in production. Always discuss loading, error, and empty states as first-class concerns.

Skipping tests in a take-home assignment. If Persistence gives you a take-home project, candidates report that untested code is treated as a red flag. Even a small number of meaningful tests demonstrates a production mindset.

Generic behavioral answers. 'I fixed a bug' is not a story. 'I noticed the dashboard was slow, profiled it with React DevTools, found the root cause in a stale memo dependency, fixed it, and shared the pattern with the team' is a story. Be specific and take clear credit for your own actions.

Not asking questions at the end. Skipping your questions can read as low interest in the role. Ask about the tech stack, the types of enterprise products the frontend team works on, or how the frontend and backend teams collaborate day to day.

Q Questions

Frequently asked

How many rounds does a Persistence Frontend Engineer interview typically have?

Candidates report going through two to four rounds, typically covering a technical screening call, one or two technical rounds on JavaScript and React, and a final HR or managerial discussion. The exact structure can vary by team and seniority level, so confirm the process with your recruiter after the first call.

Does Persistence give a coding test or online assessment?

Some candidates report an initial online coding test covering JavaScript and basic data structures, while others go straight to a live technical discussion. Take-home assignments have also been mentioned for mid-level and senior roles. Ask your recruiter which format to expect so you can prepare accordingly.

What frontend frameworks does Persistence use?

Candidates report working with React most commonly, with some teams using Angular depending on the product line. Regardless of the framework on the job description, interviews typically probe strong JavaScript fundamentals first, since those transfer across frameworks. Confirm the specific stack for your team during the interview process.

What salary can I expect for a Frontend Engineer role at Persistence?

Publicly reported figures for Persistence frontend roles vary, but the broader India market for this role runs from 5-11 LPA at entry level (0-2 years) to 12-22 LPA for mid-level engineers (3-5 years) and 24-40 LPA for senior engineers (6-9 years), based on job market data as of July 2026. Actual offers at Persistence depend on your experience, interview performance, and the specific team budget.

Are Persistence interviews conducted remotely or in person?

Early rounds are typically conducted over video call, candidates report. Later rounds, especially for Bangalore or Delhi roles, may move to in-person or a hybrid format. Confirm with your recruiter after the first round so you have time to plan accordingly.

How long does the Persistence hiring process take from application to offer?

Candidates report the process typically takes two to four weeks from the first screening call to an offer, though timelines can stretch if team schedules are busy or multiple rounds need coordinating. A polite follow-up with your recruiter after each round is a reasonable way to stay on their radar without being pushy.
