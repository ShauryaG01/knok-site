02 Most Asked Questions

Most Asked Questions

  11. How do you collaborate with backend engineers when an API is not ready yet? How do you unblock yourself?

03 Sample Answers (STAR Format)

Sample Answers (STAR Format)

Q: Walk me through the most complex UI component you have built.

*Situation:* At my previous company, we needed a multi-step employee onboarding form with many fields, several conditional sections that appeared only based on earlier answers, and real-time validation.

*Task:* I was the sole frontend engineer responsible for this component. It had to work on both desktop and mobile browsers and had to save partial progress so users could resume later.

*Action:* I split the form into step-level sub-components and used React Hook Form to manage validation. I stored intermediate state in a Zustand store so progress would persist across page refreshes. I wrote a config-driven approach where each step's fields were defined in a JSON schema, which made it easy for the product team to add or remove fields without touching the component code.

*Result:* The onboarding form went live on schedule. The team reported that support tickets related to onboarding errors dropped noticeably after launch, and the config-driven design let us add two new steps without any component code changes.

---

Q: Describe a time you found and fixed a performance problem in a React app.

*Situation:* A dashboard page at my previous company was taking a long time to become interactive after loading. Users described it as 'slow and laggy.'

*Task:* I was asked to investigate and reduce the time it took for the page to feel usable.

*Action:* I used the React DevTools Profiler to identify components re-rendering unnecessarily on every keystroke in a search box. I added React.memo to the heavy list components, moved the search state to a local component instead of global state, and added debouncing to the search input. I also found that we were importing an entire charting library on pages that did not use charts, so I switched to dynamic imports for those.

*Result:* The page felt significantly more responsive after these changes, and no further performance complaints came in for that dashboard. The Profiler showed render counts dropped sharply for the list components.

---

Q: Tell me about a time you built a feature based on a vague or incomplete requirement.

*Situation:* A product manager asked me to 'add a way for HR managers to see who has not completed their compliance training.' There was no design, no API spec, and no clarity on filters or export options.

*Task:* I needed to deliver something useful within the sprint while managing the ambiguity.

*Action:* I scheduled a quick call with the PM to agree on a minimal version: a simple table showing employees with a 'not completed' status and a CSV export button. I mocked the API response locally so I could build the frontend without waiting for the backend. I shared a working prototype after a couple of days to get early feedback before writing tests.

*Result:* The feature shipped within the sprint. The PM added it to the product demo the following week. The approach of agreeing on a minimal version first became a habit the team adopted for future ambiguous tickets.

04 Answer Frameworks

Answer Frameworks

For technical 'how would you' questions: Start with the constraint or user problem, describe your approach, and mention tradeoffs. Greytip interviewers care about product context, so tie your technical answer back to the HR software use case whenever you can. For example, if asked about rendering large lists, mention payroll tables or employee directories specifically.

For 'tell me about a time' questions: Use the STAR structure (Situation, Task, Action, Result). Keep Situation and Task brief, spend most of your time on Action, and always close with a concrete Result. Vague results like 'it went well' are weak. Even a qualitative outcome like 'the feature reduced support tickets' is better than nothing.

For system-design or architecture questions: Think out loud. Interviewers at product companies like greytip want to see your reasoning process. State your assumptions first, propose a simple design, then discuss what you would change if scale or requirements changed.

For questions about collaboration: Greytip builds a product used by a large number of companies, so cross-functional work matters. Mention specific moments where you talked to a designer, a PM, or a backend engineer and explain how that changed your approach. Avoid answers that make you sound like you work in isolation.

05 What Interviewers Want

What Interviewers Want

Greytip interviewers are typically looking for a few specific things that match the nature of the greytHR product.

Product empathy for non-technical users. greytHR is used by HR managers, not developers. Interviewers want to see that you think about usability, error states, and edge cases, not just whether the code runs.

React depth, not just React familiarity. You should be comfortable explaining re-rendering, hooks internals, state management choices, and component composition. Knowing how to use React is not enough. Interviewers want to know that you understand why it works the way it does.

Ownership and initiative. Greytip is a mid-size product company. Candidates who can take a vague ticket and deliver something useful without constant hand-holding stand out. Show that you have done this before.

Clean, maintainable code. The greytHR codebase is large and has legacy sections. Interviewers ask about component design and code reuse because they want engineers who will leave the codebase in better shape than they found it.

Awareness of B2B SaaS constraints. B2B products have complex permission models, data-heavy views, and diverse user hardware. Showing awareness of these constraints (role-based access, performance on older devices, accessibility for non-technical users) signals that you understand the product reality.

06 Preparation Plan

Preparation Plan

Week 1: JavaScript and React fundamentals

Review closures, the event loop, prototypal inheritance, and async/await. For React, make sure you can explain re-rendering, the rules of hooks, useCallback and useMemo (when to use them and when not to), and the main state management options. Write a few small components from scratch to build muscle memory.

Week 2: Build something similar to greytHR

Build a small employee list page with a search filter, a sortable data table, and a multi-step form with validation. This directly mirrors what greytHR does and gives you real examples to reference in interviews. Use React Hook Form for the form and whichever state management library you know best.

Week 3: System design and product thinking

Practice answering 'how would you build X' questions out loud. Focus on components like a payroll summary dashboard, a notification center, or a CSV export feature. Read up on frontend performance patterns: list virtualization (react-window or react-virtual), lazy loading, and bundle splitting.

Week 4: Mock interviews and STAR stories

Write down 4-5 STAR stories from your past covering: a complex component you built, a performance fix, a time you handled ambiguity, and a time you disagreed with a product decision but delivered anyway. Practice saying these out loud. Do at least one mock technical interview with a peer.

Before the interview: Research greytHR's actual product. Sign up for a trial or watch demo videos to understand the features. Being able to say 'I noticed your payroll summary screen does X' makes a strong impression.

07 Common Mistakes

Common Mistakes

Treating greytip like a startup product interview. greytHR is a mature B2B SaaS used by a large number of businesses across India. Interviewers are not looking for 'move fast and break things' answers. Show that you care about stability and the HR manager who will be confused if the UI changes without warning.

Knowing React syntax but not React internals. Many candidates can write React but struggle to explain why a component re-renders or how the reconciler works. Greytip interviewers do probe these areas. Study the 'why,' not just the 'how.'

Vague STAR answers. Saying 'I improved performance' without explaining what you measured, what you changed, and what improved as a result is a red flag. Interviewers cannot evaluate impact they cannot see.

Not asking clarifying questions. When given a coding problem or design question, jumping straight to building without asking about constraints or edge cases signals poor engineering judgment. Candidates report that greytip interviewers respond well to thoughtful questions before you start coding.

Ignoring the product context. Frontend engineering at greytip is not isolated from the product. Candidates who frame every answer in pure technical terms without mentioning the user or business outcome miss a signal interviewers value.

Underestimating take-home assignments. If greytip sends a take-home task, treat it like production code. Add basic error handling, write clean component structure, and include a short README explaining your decisions. Candidates who submit rushed work typically do not advance to the next round.
