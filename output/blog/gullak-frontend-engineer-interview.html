01 Overview

Overview

Gullak is an Indian fintech startup that helps users save through digital gold and recurring micro-investment plans. As of 2026-07-08, knok's jobradar shows 2 open Frontend Engineer roles at Gullak.

Frontend engineers at Gullak work on savings dashboards, live gold price feeds, UPI payment flows, and a product that needs to feel trustworthy when real money is on the line. 03 Sample Answers (STAR Format)

Sample Answers (STAR Format)

Q: How would you optimise a React component that re-renders on every keystroke in a savings input field?

*Situation:* At a previous payments startup, we had a gold savings calculator that triggered a live price API call on every keypress, causing visible lag on entry-level Android devices.

*Task:* I was asked to reduce unnecessary renders and API calls while keeping the calculator feeling responsive for users.

*Action:* I wrapped the input handler in a debounce so the API call fired only after the user paused typing. I memoised the calculator component with React.memo and moved the API call into a custom hook that only executed when the debounced value changed. I also used useCallback on the handler passed as a prop, so child components stopped re-rendering on every parent update.

*Result:* Render count on that screen dropped noticeably during internal testing. The calculator stayed smooth on low-end devices, and backend logs showed a clear reduction in API calls during peak usage.

---

Q: Tell me about a time you shipped a frontend change that unexpectedly affected a critical user flow.

*Situation:* At a previous company, I shipped a refactor of the payment confirmation screen to clean up the component structure. A day later, support flagged that some users were seeing a 'success' toast even when the backend returned an error.

*Task:* I needed to find and fix the root cause quickly because incorrect transaction status messages directly affect user trust and money.

*Action:* I reproduced the issue using browser devtools to inspect live network responses. The backend team had quietly changed a nested field name in one error response path without updating the API contract. I patched the response parser to handle both field names defensively, added unit tests covering all known error shapes, and worked with backend to add a shared schema check in CI.

*Result:* The fix was deployed within a few hours. The shared schema check caught two more similar mismatches the following month before they reached production.

---

Q: How do you ensure your app works reliably for users on 2G/3G connections?

*Situation:* At a previous role, product analytics showed that a large portion of active users were in Tier 2 cities on slower mobile data, and bounce rates on the main dashboard were higher for that cohort.

*Task:* I was asked to audit performance and ship concrete improvements for low-bandwidth users.

*Action:* I ran Lighthouse audits and used Chrome's network throttling to simulate 3G conditions. Changes included lazy loading non-critical components, converting images to WebP, reducing the main bundle through tree-shaking and dynamic imports, adding skeleton screens for immediate visual feedback, and setting up a service worker for offline fallback on key pages.

*Result:* Time-to-interactive on simulated 3G improved meaningfully in our internal benchmarks, and the product team reported improved retention in Tier 2 cohorts over the following quarter based on analytics.

04 Answer Frameworks

Answer Frameworks

For optimisation questions: Start with how you would diagnose and measure the problem before jumping to a fix. Walk through layered solutions, quick wins first then structural changes, and call out trade-offs. Interviewers want to see you instrument before you guess.

For feature build or system design questions: Think out loud in three passes: data flow (what state do you need and where does it live?), UI structure (component tree, loading states, error states), and edge cases (what happens when the network drops mid-transaction or the price feed is stale?).

For behavioural questions: Use STAR format. Keep Situation and Task short, around 2-3 sentences each. Spend most of your time on Action and close with a concrete, ideally measurable, Result. Vague outcomes like 'the team was happy' do not land.

For failure and error handling questions: Fintech interviewers treat these seriously. Always address what the user sees, what gets logged, and how the system recovers. Show that you think of money moving incorrectly as a trust problem, not just a UI bug.

05 What Interviewers Want

What Interviewers Want

Product empathy over pure technical depth. Gullak's users are saving real money, often for the first time. Interviewers look for engineers who care about what a confusing error message costs a user, not just whether the code passes lint.

Practical React judgment. Knowing hooks, memoisation, and state management patterns is table stakes. Candidates report that interviewers care more about when and why you reach for a tool than whether you can recite its API.

Reliability thinking for financial UX. Every question about payments or price feeds is really a question about what happens when things go wrong. Prepare to talk about error boundaries, retry logic, and user-facing failure states in detail.

Ownership and speed. Early-stage fintech startups move fast. Interviewers look for candidates who have shipped features end-to-end, handled production incidents, and can work across layers of the stack when needed.

Clear communication under pressure. Final rounds typically test whether you can explain a technical decision to a non-technical product manager or walk a junior engineer through a debugging approach. Narrate your thinking out loud during technical rounds.

06 Preparation Plan

Preparation Plan

Week 1: Core React and JavaScript fundamentals
Review rendering behaviour, hooks (useEffect, useCallback, useMemo, useReducer), common data fetching patterns, and when to use local state vs. a shared state solution. Practise explaining your choices out loud, not just coding them.

Week 2: Fintech-specific frontend topics
Study how to build secure input flows (masking sensitive fields, handling clipboard in payment forms). Read up on UPI deeplink handling and what good payment confirmation UX looks like. Think through how you would display live price data without excessive polling or stale reads.

Week 3: Performance and accessibility
Run Lighthouse on a personal project. Practise explaining your Core Web Vitals scores and what you would change. Review WCAG basics for financial data, particularly colour contrast and ARIA labels on charts and dynamic price updates.

Week 4: Mock interviews and behavioural preparation
Prepare 4-5 STAR stories covering: a production bug you debugged, a feature you owned end-to-end, a performance improvement you drove, and a time you disagreed with a technical decision. Do at least one timed live coding session on a shared editor or whiteboard.

07 Common Mistakes

Common Mistakes

Skipping the 'why' in optimisation answers. Saying 'I used React.memo' without explaining what problem it solved or how you measured the impact makes the answer feel rehearsed rather than real.

Treating payment errors like regular UI errors. Answering 'just show a toast and let the user retry' for a mid-transaction failure signals you have not thought about user trust or the financial consequence of a stale transaction state.

Over-engineering the take-home assignment. Candidates report that Gullak reviewers value clean, readable code and solid error handling over impressive but unnecessary abstractions. Finish the core requirements before adding extras.

Ignoring mobile and low-bandwidth scenarios. If you only test on a fast desktop browser, your answers will miss the context of Gullak's actual users. Always mention device type and network conditions when discussing performance.

Vague STAR answers. Outcomes like 'it improved a lot' or 'the team was happy' do not land. Even a relative statement ('render time dropped by roughly half in our internal tests') is more credible than a vague positive.

Never asking product questions. Candidates who treat every question as purely technical and never ask 'what is the user trying to accomplish here?' miss the chance to show the product empathy that fintech teams value.
