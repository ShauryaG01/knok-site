03 Sample Answers (STAR Format)

Sample Answers (STAR Format)

Q: Describe a time you improved frontend performance on a product.

*Situation:* I was working on an e-commerce listing page that loaded slowly on mid-range Android devices, which are common among users in tier-2 cities.

*Task:* My goal was to reduce Largest Contentful Paint (LCP) and improve perceived speed without a full redesign.

*Action:* I profiled the page with Chrome DevTools and found three bottlenecks: images were not lazy-loaded, a large third-party analytics bundle was blocking the main thread, and the product grid was rendering all cards upfront. I added lazy loading for images below the fold, moved the analytics script to load asynchronously, and replaced the grid with a virtualized list using react-window.

*Result:* LCP improved significantly as measured in our internal RUM dashboard, and the bounce rate on that page dropped noticeably in our analytics. The change shipped without any regressions.

---

Q: How would you design a cart system for a food delivery app?

*Situation:* In a frontend design round, I was asked to build a cart that works across multiple pages, survives a browser refresh, and handles items going out of stock mid-session.

*Task:* I needed to outline the state management approach, persistence strategy, and backend sync mechanism.

*Action:* I proposed a global React context backed by a reducer for in-session updates, localStorage for offline persistence, and a debounced API call to sync the cart server-side every few seconds. For out-of-stock items, I designed an optimistic UI that marks those items as unavailable with a non-blocking toast, rather than halting the checkout flow entirely.

*Result:* The interviewer appreciated the explicit handling of optimistic updates and the clean separation between local and server state. The discussion moved into conflict resolution strategies, which I handled well by referencing familiar patterns like last-write-wins.

---

Q: A junior developer introduced a memory leak in useEffect. How did you handle it?

*Situation:* During a code review, I found a component attaching a window resize listener inside useEffect without ever removing it, causing listeners to accumulate on every re-render.

*Task:* I needed to fix the bug and help the junior developer understand the pattern clearly enough to avoid repeating it.

*Action:* I walked them through the cleanup function in useEffect, demonstrating how returning a function that calls removeEventListener prevents the leak. I then extracted a reusable custom hook called useWindowResize so the safe pattern became the default going forward.

*Result:* The leak was resolved, the junior developer adopted the hook in their next components, and the issue no longer appeared in our memory timeline during the next performance audit.

04 Answer Frameworks

Answer Frameworks

For 'explain how X works' questions: Start with a one-sentence definition, add a concrete analogy or real example, then describe a situation where that detail actually mattered. Zomato interviewers typically want to see if you can teach the concept, not just recite it from memory.

For system or component design questions: Clarify requirements first, state your assumptions, sketch the component tree or data flow, then discuss tradeoffs. Candidates report that saying 'I would choose X over Y because of Z constraint' lands much better than describing only one approach without justifying it.

For debugging or performance questions: Measure before fixing. Name the tool (DevTools, Lighthouse, RUM), isolate the bottleneck, apply the highest-impact fix, and verify with the same measurement. Saying you would 'just optimise it' without naming a specific metric signals shallow experience.

For behavioral questions: Use STAR: Situation (brief), Task (what you owned), Action (spend most of your time here), Result (concrete and observable). If you have no metric, describe a qualitative change visible to the team or users. 'We had no formal measurement, but the team saw noticeably faster loads in testing' is honest and still specific.

05 What Interviewers Want

What Interviewers Want

Zomato's frontend interviewers are typically looking for four things.

Depth on JavaScript and React fundamentals. Not memorized answers, but reasoning from first principles. If you know that React's reconciliation algorithm is designed to run in O(n) time, be ready to explain why that choice matters for long lists and how it should inform your component structure.

Product thinking alongside engineering. Because Zomato is a consumer product company, candidates report that interviewers often probe whether you understand the user impact of a technical decision. Connecting a performance fix to faster load times on a 4G connection in smaller cities will land better than a purely technical answer.

Ownership and composure under pressure. Interviewers often push back on your answer or add new constraints mid-question. This is intentional. They want to see how you handle ambiguity and whether you can adapt your solution without losing your thread.

Clear verbal communication. Frontend design rounds are typically conducted verbally or on a shared whiteboard. Thinking aloud, naming your assumptions, and organizing your answer before you start coding all signal seniority to the panel.

06 Preparation Plan

Preparation Plan

Weeks 1-2: Core JavaScript and React
Revisit closures, the event loop, prototypal inheritance, and async patterns (promises, async/await). For React, focus on the reconciliation algorithm, hooks internals (how useState and useEffect actually work), and performance patterns like memoization and list virtualisation.

Week 3: Frontend system design
Practice designing components and page architectures out loud. Use Zomato-relevant scenarios: a live order tracker, a paginated restaurant feed, a multi-step checkout. For each, think through state management, data fetching, error states, and accessibility requirements.

Week 4: Performance and tooling
Get comfortable reading Lighthouse reports and Chrome DevTools performance profiles. Be ready to explain what TTI, LCP, and CLS mean and how to improve each. Understand how code splitting, lazy loading, and tree shaking work at a conceptual level.

Behavioral prep (throughout)
Prepare three to five STAR stories from your past work. Cover at minimum: a performance improvement, a conflict you resolved, a complex feature you shipped, and a time you mentored or unblocked a teammate. Zomato interviews typically include at least one behavioral round.

07 Common Mistakes

Common Mistakes

Jumping to code before clarifying requirements. Candidates often start writing JSX before asking what the component must handle: loading states, empty states, mobile layout, accessibility. Take the first two minutes to clarify scope before writing anything.

Treating React as a black box. Saying 'useEffect runs after render' is a starting point, not an answer. Interviewers at product-focused companies typically want you to explain the design reasoning behind the behavior, not just recite it.

Ignoring the user in technical answers. A purely engineering answer to 'how would you improve page load speed' can miss what Zomato actually cares about. Connecting your solution to user experience, such as faster loads on a 4G connection, signals genuine product awareness.

Over-engineering design questions. Proposing a micro-frontend architecture for a simple search bar signals a mismatch between problem complexity and your solution. Start simple, then add layers only when the interviewer explicitly pushes for more scale.

Giving vague behavioral answers. 'I improved performance by a lot' is not a result. If you have no metric, say 'we had no formal measurement, but the team observed noticeably faster page loads in testing.' That is honest and still concrete.

Not asking questions at the end. Zomato interviewers typically expect genuine curiosity about the team, the tech stack, or upcoming product challenges. Asking nothing at the close signals low interest in the role.

Q Questions

Frequently asked

How many rounds does a Zomato Frontend Engineer interview typically have?

Candidates report a process that typically runs three to five rounds. This usually includes a recruiter or HR screen, one or two technical rounds (coding and frontend design), and a hiring-manager conversation. The exact format varies by team and seniority level, so confirm the structure with your recruiter after the first call.

What salary can I expect as a Frontend Engineer at Zomato?

Based on knok jobradar data for Frontend Engineers across India, mid-level roles (3-5 years) fall in the 12-22 LPA range, and senior roles (6-9 years) in the 24-40 LPA range. For Zomato-specific figures, publicly reported data on Glassdoor and levels.fyi is the best starting point, since actual compensation varies by team, level, and negotiation.

Does Zomato focus more on DSA or frontend-specific questions?

Candidates report that Zomato's frontend interviews lean toward JavaScript and React depth, UI system design, and performance optimisation rather than classical data structures and algorithms. Basic problem-solving ability is still tested, so be comfortable with arrays, strings, and patterns like debouncing and throttling, which come up naturally in frontend scenarios.

Is Zomato open to candidates from cities outside Bangalore?

Zomato's core engineering is concentrated in Bangalore, which has the highest share of open Frontend Engineer roles. Candidates report that some teams offer remote or hybrid arrangements, but this varies significantly by team. Check the specific listing and ask the recruiter early in the process to avoid surprises about location expectations.

How important is system design for a mid-level Frontend Engineer role?

For mid-level candidates (3-5 years experience), system design is typically tested at the component and page level, not at distributed systems scale. Expect to design something like a search interface, a dynamic restaurant feed, or a cart system. Senior candidates face more complex frontend architecture questions around state management across large apps and performance at scale.

What should I do if I keep failing the technical round?

The most commonly reported gaps are weak JavaScript fundamentals (especially closures, the event loop, and async behavior) and difficulty thinking out loud during problem-solving. Recording yourself explaining a solution and watching it back helps surface gaps in verbal reasoning. Practicing with questions from product-tech companies in a similar category also helps you calibrate your depth against what interviewers actually expect at this level.
